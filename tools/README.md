# Hub metadata tools

The hub's data model lives in one file, `tools/objects.yml`. Two scripts turn it into
Salesforce metadata under `sfdevops-app/main/default/`. Edit the YAML or the scripts, then
regenerate. Never hand-edit a generated file: the next run overwrites it.

Requirements: Python 3 with PyYAML (`py -m pip install pyyaml`). Run the scripts from the hub
root (the folder that holds `sfdx-project.json`).

## Regenerate

```bash
py tools/gen_metadata.py       # objects, fields, list views, validation rule, layouts, object tabs
py tools/gen_permissions.py    # the four permission sets
py tools/gen_metadata.py --check && py tools/gen_permissions.py --check   # CI: exit 1 if stale
```

The scripts are idempotent:

- Every generated file carries a `Generated by tools/gen_...py` comment just inside its root
  element. The scripts rewrite or prune only files that carry their own marker, and they
  refuse to overwrite a file without it.
- A file is rewritten only when its content changes. A second run reports `0 wrote`.
- A generated file that the YAML no longer produces (a field you removed, say) is pruned.
  Pass `--no-prune` to keep it. Pruning a file does not delete the component from an org. Use
  a destructive deploy for that.

### What is generated and what is hand-authored

| Path under `sfdevops-app/main/default/` | Source |
| --- | --- |
| `objects/*/` (object, `fields/`, `listViews/All`, `validationRules/Append_Only`) | `gen_metadata.py` |
| `objects/CDO_Settings__c/` (hierarchy custom setting) | `gen_metadata.py` (`custom_settings:` in the YAML) |
| `layouts/*` (21, one per custom object) | `gen_metadata.py` |
| `tabs/<Object>.tab-meta.xml` (13 object tabs) | `gen_metadata.py` (`OBJECT_TABS`) |
| `permissionsets/*` (4) | `gen_permissions.py` |
| `tabs/CDO_Pipeline`, `CDO_Release_Board`, `CDO_Delivery_Metrics`, `CDO_Data_Deploy` | hand-authored |
| `quickActions/*` (2), `flexipages/*` (6), `applications/SF_DevOps` | hand-authored |
| `customPermissions/*` (5), `externalCredentials/*`, `namedCredentials/*` | hand-authored |
| `permissionsetgroups/*` (4) | hand-authored |

The YAML holds the data model only. The UI settings live at the top of `gen_metadata.py`:
`OBJECT_TABS` (which objects get a tab, and its motif) and `LAYOUT_ACTIONS` (record actions on a
layout). Motif strings must match Salesforce's list exactly, for example
`Custom57: Building Block`.

### Rules the generators enforce

- **A Percent field never gets a `defaultValue`.** A metadata default is a fraction (`0.85` =
  85 %), but values written through the API are literal (`85` = 85 %). `75` as a default stores
  7500 %. The generator refuses a Percent default in the YAML.
- Picklists are restricted unless the YAML says `restricted: false`. A value's label is its API
  name with `_` replaced by a space. A restricted picklist has no "not known yet" value, so
  `Health_Status__c` has no default, and code leaves it blank until something has deployed.
- Lookups use `deleteConstraint` SetNull, so a required lookup is rejected (it would need Restrict).
- Master-detail fields get `relationshipOrder` 0, are not reparentable, and the detail object
  must be `sharing: ControlledByParent`.
- Field-level security is written for every field except required and master-detail fields
  (Salesforce rejects FLS on those) and the custom setting's fields (the setting is granted with
  `customSettingAccesses`). A field deployed without a permission set is invisible to every
  profile, including System Administrator, until a permission set grants it.
- `CDO_Audit_Event__c` is append-only: the `Append_Only` validation rule (`NOT(ISNEW())`)
  blocks every update, and no permission set grants Edit or Delete on it.

## Deploy order

Deploy to the hub in this order. Each step needs the ones before it.

| # | What | Why it waits |
| --- | --- | --- |
| 1 | `objects` (with the custom setting), `customPermissions`, `externalCredentials`, `namedCredentials` | Nothing. The Named Credential needs the External Credential; one deploy handles both |
| 2 | `classes` | Apex references the objects and fields |
| 3 | `lwc` | Components import Apex methods and fields |
| 4 | `quickActions` | Each action names its LWC (`cdoPromoteAction`, `cdoPromoteDeployAction`) |
| 5 | `layouts` | The Work Item layout lists the quick actions. **Deploy them first, in a separate deploy** |
| 6 | `flexipages` | The pages place the LWCs |
| 7 | `tabs` | The four app tabs open flexipages. The 13 object tabs only need step 1 |
| 8 | `applications` | The app lists the 17 tabs and assigns the two record pages |
| 9 | `permissionsets` | They grant Apex classes, the app, the tabs, the custom permissions and the GitHub principal |
| 10 | `permissionsetgroups` | Each group bundles permission sets |

```bash
set -o pipefail     # never let `| tail` hide a failed deploy
D=sfdevops-app/main/default
ORG=sfp-hub
sf project deploy start -o $ORG --source-dir $D/objects --source-dir $D/customPermissions \
  --source-dir $D/externalCredentials --source-dir $D/namedCredentials --wait 30
sf project deploy start -o $ORG --source-dir $D/classes             --wait 30
sf project deploy start -o $ORG --source-dir $D/lwc                 --wait 30
sf project deploy start -o $ORG --source-dir $D/quickActions        --wait 30
sf project deploy start -o $ORG --source-dir $D/layouts             --wait 30
sf project deploy start -o $ORG --source-dir $D/flexipages          --wait 30
sf project deploy start -o $ORG --source-dir $D/tabs                --wait 30
sf project deploy start -o $ORG --source-dir $D/applications        --wait 30
sf project deploy start -o $ORG --source-dir $D/permissionsets      --wait 30
sf project deploy start -o $ORG --source-dir $D/permissionsetgroups --wait 30
```

Check every step's exit status. If the CLI loses its connection while polling, it can exit
non-zero on a deploy the org accepted. The deploy id is the durable record:
`sf project deploy report -o $ORG -i <id>` and believe `Status: Succeeded`.

### Traps

- **A layout cannot reference a quick action created in the same deploy.** Salesforce rolls the
  whole deploy back. That is why quick actions (step 4) and layouts (step 5) are separate deploys.
  Before the quick actions exist, deploy every layout except
  `CDO_Work_Item__c-Work Item Layout`. (A check-only validation that put both in one deploy
  passed in our scratch org, but the spec records a real rollback, and separate deploys cost
  nothing.)
- **A component with no page deploys fine but nobody can reach it.** Every LWC except the
  `cdoUtils` module is placed:

  | LWC | Where |
  | --- | --- |
  | `cdoPipeline`, `cdoNewWorkItem`, `cdoGovernance` | `CDO_Pipeline_Home` (tab Pipeline) |
  | `cdoReleaseBoard` | `CDO_Release_Board` (tab Release Board) |
  | `cdoDora` | `CDO_Delivery_Metrics` (tab Delivery Metrics) |
  | `cdoDataDeployer` | `CDO_Data_Deploy` (tab Data Deploy) |
  | `cdoWorkItemCommandCenter`, `cdoCommit`, `cdoDeploymentSteps` | `CDO_Work_Item_Record_Page` |
  | `cdoPromote` | `CDO_Promotion_Record_Page` |
  | `cdoPromoteAction`, `cdoPromoteDeployAction` | Quick actions Promote / Promote & Deploy on the Work Item layout, shown in the record page's highlights panel |

  A deploy that succeeds does not prove this. Open the app and click through every tab and page.
- **App visibility is a separate grant from tabs.** `CDO_User` grants `applicationVisibilities`
  for `SF_DevOps`. Without it the App Launcher is empty even with every tab, object and class.
- **`PermissionSetGroup.description` is at most 255 characters.**
- **Quick-action LWCs must match the action subtype.** Both quick actions are `ScreenAction`, so
  each LWC's `js-meta.xml` needs target `lightning__RecordAction` with
  `<actionType>ScreenAction</actionType>`. App-page components need `lightning__AppPage`.
  Record-page components need `lightning__RecordPage`.
- **No secret lives in metadata.** The Named Credential `GitHub_API` sends
  `Authorization: {!'Bearer ' & $Credential.GitHub_API_Credential.Token}`. The `Token`
  authentication parameter of principal `GitHub_PAT` is set through the API by
  `sf-pipeline/scripts/bootstrap-secrets.sh`. A user's callouts work only with a permission set
  that grants `externalCredentialPrincipalAccesses` for `GitHub_API_Credential-GitHub_PAT`
  (`CDO_Developer`, `CDO_Release_Manager`, `CDO_Pipeline_Admin`).

## Permission sets and groups

| Permission set group | Permission sets |
| --- | --- |
| `CDO_Developer_Access` | `CDO_User`, `CDO_Developer` |
| `CDO_Release_Manager_Access` | `CDO_User`, `CDO_Developer`, `CDO_Release_Manager` |
| `CDO_Pipeline_Admin_Access` | `CDO_User`, `CDO_Developer`, `CDO_Pipeline_Admin` |
| `CDO_Admin_Access` | all four |

The hub's callback integration user holds `CDO_Pipeline_Admin`, because it grants the REST
resources (`CDO_CallbackResource`, `CDO_MergeStatusResource`, `CDO_SourceMemberResource`).
Object access, class lists and custom permissions per set are defined at the top of
`gen_permissions.py`.
